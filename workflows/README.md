# ComfyUI workflows

Node graphs for generating toon plates, as an alternative to
`scripts/generate-toon-page.py` (which talks to the RunComfy **model API**, not
to ComfyUI).

| File                         | Format | Use                                                             |
| ---------------------------- | ------ | --------------------------------------------------------------- |
| `redsmile-seedream.api.json` | API    | Generated by `build-comfy-plate.py` — the last page built       |
| `redsmile-seedream.json`     | UI     | Canvas copy, still on the legacy node + Lite — see below        |
| `nero-seedream.api.json`     | API    | `POST /prompt`, or CI — named inputs, no widget-order ambiguity |
| `nero-seedream.json`         | UI     | Drag onto the ComfyUI canvas and edit visually                  |

## One generator, not one file per page

The graph is identical for every page — only the prompt, which reference sits in
which slot, and the output name change — so those three are arguments to
`scripts/build-comfy-plate.py`, not a new file:

```bash
npm run comfy-page -- \
  --prompt-file docs/story/red-smile/prompts/page-10-lift-drain.txt \
  --ref halina --ref marcus --ref page08 \
  --prefix redsmile-marcus/page-10 \
  --out workflows/redsmile-seedream.api.json --submit
```

`scripts/build-comfy-plate.py` **generates** the graph rather than storing one
per page, so `redsmile-seedream.api.json` is an output, not a hand-maintained
file — it holds whatever page was built last. Re-run the command to get another.

Without `--submit` nothing is queued: the file is written and the `curl` printed.
That is the default because an API-node run costs real credits.

`--ref` is repeatable and takes an **alias** from the `REFS` table at the top of
the script, or any filename already in the ComfyUI `input/` dir. Order **is**
what the prompt's PIN clause means by "Image 1 / Image 2 / Image 3", previous
page last — on page 10 Halina comes first because that page pins her first, and
swapping her with Marcus ages the wrong person.

Each `LoadImage` gets a `_meta.title` naming the alias you passed. That matters:
ComfyUI renames every upload to the sha256 of its bytes, so
`19f0f1f6…c396.png` records nothing about what it is, and a stale title is worse
than none.

Adding a page is therefore: write the prompt `.txt` under
`docs/story/<series>/prompts/`, add the previous plate to `REFS`, run the
command. **A second workflow file is never the answer** — two copies of one
graph start identical and drift, which is how these files spent a day carrying
"Nero sheet" and "Eve sheet" titles.

## Guard rails the generator enforces

- **3.68 MP floor.** Seedream 4.5 / 5.0 reject anything smaller, and the node
  reports it as a `ValueError` only after the graph is queued. The old
  1024x1792 is 1.84 MP — exactly half — so the default is now **1472x2624**
  (3.86 MP, aspect 0.5610 against the plate's 0.5618, both axes multiples of
  16), and the graph ends with an `ImageScale` to **800x1424** so the output is
  a drop-in for `swap-toon-page.js`. `seedream-4-0` gets the lower 0.92 MP floor.
- **Unknown `--ref`** fails with the alias list rather than writing a graph that
  loads with an empty `LoadImage`.
- **Over 10 references** fails; that is the node's limit.
- Over ~600 prompt words warns — past that Seedream scatters detail.

## Reference slots

`ByteDanceSeedreamNodeV3` takes references in numbered autogrow slots:

```
LoadImage (Halina sheet)  → model.images.image_1 ─┐
LoadImage (Marcus sheet)  → model.images.image_2 ─┼→ Seedream
LoadImage (page 8 plate)  → model.images.image_3 ─┘  → flatten → ImageScale → SaveImage
```

There is no `ImageBatch` chain any more — `model.images.image_N` _is_ the
"Image N" the prompt's PIN clause names.

Those dotted keys are not a convention to copy blindly — they are what
`finalize_prefix` actually produced for a live graph, recovered from a ComfyUI
`Export (API)`. Pro also carries **no** `model.max_images` and no
`model.fail_on_partial`: it is declared `supports_batch=False`, which is the same
reason it cannot be sent `sequential_image_generation`.

Saves to `<--out>_00001_.png` in the ComfyUI output dir, plus `<--out>-raw_00001_.png`.

### The `LoadImage` names are content hashes, not readable filenames

ComfyUI renames anything uploaded through a `LoadImage` widget to the sha256 of
its bytes, so the graphs carry names like
`19f0f1f640d5016041f90d7fac523ecd2f67fba45670b55e1e4b7b954628c396.png`. Nothing
in the filename says which reference it is — **the `_meta.title` on each
`LoadImage` is the only record**, so keep those titles accurate:

`REFS` in `scripts/run-comfy-page.js` is that record — one alias per upload:

| Alias    | Reference    | `ComfyUI/input/` name |
| -------- | ------------ | --------------------- |
| `halina` | Halina sheet | `19f0f1f6…c396.png`   |
| `marcus` | Marcus sheet | `be8903d6…38d4.png`   |
| `page08` | page 8 plate | `9bdb1524…349c.png`   |

Each new page adds one line: the plate that page follows. Nothing else in the
graph changes.

**Every one of these must be the un-watermarked plate.** Feed the watermarked
WebP from `public/` and Seedream inks `twentyseven.pictures` into the new page.
The un-watermarked exports live at `~/Downloads/redsmile-marcus-page-0{8,9}.png`;
regenerate one from the source roll if it is gone.

A hash also has no stable meaning across machines: re-upload the same file to a
different instance and you get the same name, but a **different** file uploaded
first will already own a different one. If a graph loads with an empty
`LoadImage`, the file is simply not in that instance's `input/` — re-upload and
paste the new hash in.

## Greyscale flatten is in the graph

Seedream returns a faint colour cast on every generation — the page 8 roll
measured **1.68** (of 255) mean per-pixel deviation from grey, which reads as a
blue tone on dark plates. The RED SMILE template flattens it before saving,
so `swap-toon-page` gets a neutral plate and the `magick -colorspace Gray` pass
is no longer needed:

```
Seedream → ImageToMask ×3 (red / green / blue) → MaskToImage ×3
        → ImageBlend(R, G, 0.7708) → ImageBlend(·, B, 0.0722) → SaveImage
```

**Core nodes only, on purpose.** ComfyUI ships no grayscale node — the obvious
`ImageDesaturate` comes from Comfy Essentials / WAS, and a graph in this repo
must load on a stock install. The two `blend_factor` values are not arbitrary:
`ImageBlend` in `normal` mode computes `image1*(1-f) + image2*f`, so

```
f = 0.7708 → 0.2292 R + 0.7708 G
f = 0.0722 → 0.9278 × that + 0.0722 B = 0.2126 R + 0.7152 G + 0.0722 B
```

which is Rec.709 luma to within 0.02/255. Change either number and the plate is
no longer a luminance-correct grey — a plain channel average crushes the greys
in heavy ink washes.

A second `SaveImage` keeps the **untouched** output at `…-raw`. The flatten is
lossy in principle and API-node runs cost credits; losing a good roll to a bad
conversion is not worth saving one file. Verify any plate with:

```bash
magick <file> \( +clone -colorspace Gray \) -compose difference -composite \
  -colorspace Gray -format "%[fx:mean*255]\n" info:   # 0 = truly neutral
```

## Nero

`nero-seedream.json` / `.api.json` predate all of the above: they still use the
legacy `ByteDanceSeedreamNode` with one batched IMAGE input, and there is no
runner for them. Both build the same graph:

```
LoadImage (Nero sheet)  ─┐
LoadImage (Eve sheet)   ─┼→ ImageBatch → ImageBatch → ByteDanceSeedreamNode → SaveImage
LoadImage (prev page)   ─┘                                  ▲
                                       prompt widget (FORMAT / PIN / PANELS / ANATOMY)
```

## Reference order matters

`ByteDanceSeedreamNode` takes one batched IMAGE input, and the prompt refers to
"Image 1 / Image 2 / Image 3". The two `ImageBatch` nodes are chained so the
order comes out **Nero sheet, Eve sheet, previous page** — matching the PIN
clause. Re-wire them and the pins point at the wrong pictures.

Drop the three files into `ComfyUI/input/` first, or re-pick them in each
`LoadImage`:

- `nero-character-sheet.png`
- `eve-character-sheet.png`
- `nero-previous-page.png` — the last published plate, so rain, gutters and ink
  carry over. Pull it from `content/toons/nero/config.json` → last `file`, or
  from `cdn-backup/toons/nero/assets/`.

## Model name — Pro needs the V3 node, Lite does not

Pages 1-9 were generated with **`bytedance/seedream-5.0-pro`** through the
RunComfy model API, so Pro is what keeps the ink matching. The `.api.json` files
run Pro on `ByteDanceSeedreamNodeV3`; the two UI files are still on
`model: "seedream 5.0 lite"` and the legacy node, which is a fallback that runs
but **will not match the existing pages**.

The split is not a preference — the legacy node physically cannot reach Pro.

`ByteDanceSeedreamNode` (the flat-widget class, still what ComfyUI v0.33.3
instantiates for this node type) builds its payload as:

```python
sequential_image_generation=sequential_image_generation,
sequential_image_generation_options=Seedream4Options(max_images=max_images),
```

No `is_pro` guard, so the field always goes out — and the Seedream 5.0 **Pro**
endpoint rejects that parameter by name:

```
Exception: API Error: The parameter `sequential_image_generation` specified in the
request are not valid: the parameter `sequential_image_generation` is not supported
by the current model. (Type: BadRequest)
```

Setting it to `"disabled"` does not help. The parameter's **presence** is the
error, and no widget on that node can remove it. Lite accepts the field, so
Lite runs; Pro cannot, on this node.

**To run Pro**, use the node the picker lists as **"ByteDance Seedream 4.5 &
5.0"** (`ByteDanceSeedreamNodeV3`), which guards it:

```python
sequential_image_generation=None if is_pro else sequential_image_generation,
```

That node is a **different graph shape** — no flat `sequential_image_generation`
widget (the per-model inputs are nested under a `DynamicCombo`), and reference
images arrive as an autogrow `images` list instead of one batched IMAGE, so the
`ImageBatch` chain goes away. Rebuild it from the picker rather than editing
these files by hand: the `model` value is a serialized dict the frontend writes,
and hand-authoring it is how you get a second round of `BadRequest`.

**Telling the two apart in a saved workflow:** if node 6 lists
`sequential_image_generation` among its own widgets, it is the old class.

### Swapping node 6 for the Pro-capable node

Everything except node 6 survives, so do this in the UI rather than by editing
the JSON — `V3` declares its reference images as an `IO.Autogrow.Input("images",
template=IO.Autogrow.TemplateNames(IO.Image.Input("image"), names=[f"image_{i}"
…]))` nested inside an `IO.DynamicCombo.Input("model")`, and the resulting
prompt-JSON keys are dot-joined by `finalize_prefix` at load time. Hand-writing
those keys is guesswork; the frontend writes them correctly for free.

1. Delete nodes **4** and **5** (the `ImageBatch` chain). `V3` takes reference
   images in separate numbered slots, so batching them is no longer how order is
   established — **slot order is the order**, and it still has to be
   sheet, sheet, previous page to match the PIN clause.
2. Delete node **6**.
3. Add **"ByteDance Seedream 4.5 & 5.0"** from the node picker.
4. Set `model` = **seedream 5.0 pro**, `size_preset` = **Custom**,
   width **1472**, height **2624**, `watermark` **off**, `max_images` **1**.
   Paste the prompt from `docs/story/red-smile/prompts/`.
5. Connect the three `LoadImage` nodes into its image slots in order; the node
   grows a new slot as each one is filled.
6. Connect its IMAGE output to nodes **8, 9, 10** (the channel splits) and to
   node **16** (`Save raw`). The flatten chain, the `ImageScale` to 800×1424 and
   both `SaveImage` nodes need no changes.

Then export the workflow and commit both formats over these files. Pro's width
ceiling is 3136 and height 4992, so 1472×2624 stays legal.

## Size

The prompt names the plate size (1008×1792 for Nero, 800×1424 for RED SMILE)
because that phrasing is what holds the three-panel vertical shape. The node's
`width`/`height` are something else entirely, and there are two floors to clear:

- **minimum width 1024** — Nero renders 1024×1792 for this reason.
- **minimum resolution 3.68 MP for Seedream Pro.** 1024×1792 is 1.84 MP and the
  node rejects it outright:

  ```
  ValueError: Minimum image resolution for the selected model is 3.68MP, but 1.84MP provided.
  ```

The RED SMILE graphs therefore render **1472×2624** (3.86 MP, aspect 0.5610
against the plate's 0.5618, both axes multiples of 16) and end with an
`ImageScale` down to **800×1424** — so the saved plate is a drop-in for
`swap-toon-page.js` and matches every other Marcus page byte-for-byte in shape.
The `…-raw` save keeps the full-resolution generation.

Do not simply raise the numbers to clear 3.68 MP and leave it there: a plate
that reaches `swap-page` at 1472×2624 still works, but it lands in the reader at
a different pixel size from its neighbours for no gain — the CDN WebP just gets
bigger.

## After a good generation

```bash
# replace an existing page, keeping its captions, coordinates and audio
node scripts/swap-toon-page.js ~/Downloads/plate.png --toon nero --page 21 --publish

# or append a new page
npm run add-image -- ~/Downloads/plate.png --toon nero --config --upload
```

Then flatten the colour cast and re-level audio if the page brought new clips:

```bash
magick <src> -colorspace Gray -colorspace sRGB /tmp/flat.png   # Seedream tints blue
npm run normalise-audio -- nero
```

## Caveats

- **Widget order** — the UI file lists `widgets_values` positionally, so a node
  update that adds or reorders an input silently shifts the values. After
  loading, confirm the prompt is in the prompt box and the size reads 1024×1792.
  The API file is immune to this; prefer it when scripting.
- The seed widget carries an extra `"fixed"` control value in the UI format.
  That is the frontend's `control_after_generate`, not a node input, and it has
  no counterpart in the API file.
- API-node runs need Comfy API credits and an account signed in to the ComfyUI
  frontend; they are billed by ComfyUI/RunComfy, not by this repo's `.env`.
